# NAME TAG 제품 기획서

> 개정판: Multi-user / Authentication 반영


## 문서 목적

이 문서는 NAME TAG가 **무엇을 만드는 제품인지**, 사용자가 어떤 경험을 하는지, 그리고 제품의 핵심 데이터/기능 관계를 정의한다.

# 1. 프로젝트 개요

## 1.1 서비스명

**NAME TAG**

## 1.2 서비스 정의

> **AI와 대화하며 하나의 사업과 브랜드를 만들어가는 AI Brand Workspace**

NAME TAG는 사용자가 자신의 사업 아이디어, 서비스, 프로젝트 또는 개인 사업에 대해 AI와 대화하면, AI가 대화 내용을 바탕으로 사업 구조와 브랜드 전략을 정리하고 시장조사, 고객 분석, 브랜드 전략, 비주얼 아이덴티티, 브랜드 에셋까지 하나의 연결된 Workspace에서 구축할 수 있도록 지원하는 **multi-user AI Brand Workspace**다.

단순히 브랜드 이름이나 로고를 생성하는 것이 아니라,

```text
아이디어
  ↓
사업
  ↓
시장
  ↓
고객
  ↓
브랜드
  ↓
디자인
  ↓
실제 결과물
```

을 하나의 연결된 시스템으로 관리하는 것을 목표로 한다.

핵심 원칙은 다음과 같다.

> **Chat은 입력 방식이고, Workspace가 제품이다.**

# 1-A. 계정과 사용자 데이터 분리

로그인 기능은 단순히 로그인 화면을 추가하는 기능이 아니다. NAME TAG에서 생성되는 모든 사용자별 데이터의 **소유권과 접근 범위**를 정의하는 기반 기능이다.

기본 구조는 다음과 같다.

```text
User
  │
  ├── Brand 1
  │    ├── BrandState
  │    ├── Conversations
  │    ├── Research
  │    ├── Documents
  │    ├── Assets
  │    └── History
  │
  └── Brand 2
       └── ...
```

한 사용자가 여러 개의 브랜드/프로젝트를 만들 수 있도록 한다. 따라서 `User = Brand`로 강하게 묶지 않는다.

### 향후 협업까지 고려한 소유권 모델

```text
User
  ↓
BrandMember
  ↓
Brand
```

초기에는 다음 역할만 사용한다.

| Role | 권한 |
|---|---|
| owner | 브랜드 전체 관리, 멤버 관리, 중요 변경 승인 |
| editor | 브랜드/문서/리서치 수정 |
| viewer | 조회만 가능 |

초기 서비스는 개인 사용을 중심으로 운영하더라도 `BrandMember`를 두어 향후 팀 기능 확장의 기반을 만든다.

### 계정이 필요한 이유

* 사용자의 브랜드와 대화를 분리하여 저장할 수 있다.
* 여러 기기에서 같은 Workspace를 이어서 사용할 수 있다.
* Research/Asset/AI 사용량을 사용자와 Brand 단위로 집계할 수 있다.
* 다른 사용자의 브랜드 데이터를 조회하거나 수정하지 못하도록 권한을 적용할 수 있다.
* 향후 유료 플랜, 사용량 제한, 팀 협업을 추가할 수 있다.

### 기본 사용자 흐름

```text
Landing
  ↓
Sign Up / Login
  ↓
My Brands
  ↓
Create Brand
  ↓
Workspace
  ↓
AI Consultant / Research / Assets
```

기존 브라우저에서 로그인 없이 작성된 legacy localStorage 데이터가 있는 경우 첫 로그인 시 해당 데이터를 새 Brand로 이전할 수 있는 migration flow를 제공한다.

# 2. 문제 정의

## 2.1 기존 AI 활용의 문제

사용자는 ChatGPT와 같은 생성형 AI를 이용하여 다음과 같은 작업을 할 수 있다.

* 사업 아이디어 정리
* 시장조사
* 경쟁사 분석
* 브랜드 네이밍
* 브랜드 스토리 작성
* 로고 생성
* 사업계획서 작성
* 마케팅 문구 작성

하지만 각각의 작업이 대화 단위로 분리되기 쉽다.

예를 들어 사용자가 처음에는

> "대학생을 위한 AI 공부 서비스를 만들고 싶다."

라고 했다가 이후 타겟을 직장인으로 변경하면,

* Persona
* Positioning
* Brand Story
* Tone
* Visual Direction
* Logo

등 기존 결과물의 관계를 다시 정리해야 한다.

일반적인 대화형 AI에서는 이러한 관계와 변경 이력을 사용자가 직접 관리해야 한다.

# 3. NAME TAG가 해결하는 문제

NAME TAG는 사용자의 브랜드를 하나의 **BrandState**로 관리한다.

```text
Business
   ↓
Market
   ↓
Customer
   ↓
Brand
   ↓
Visual
   ↓
Assets
```

각 정보는 서로 연결되어 있으며 하나의 정보가 변경되었을 때 영향을 받는 다른 정보도 파악할 수 있도록 한다.

예:

```text
Target 변경
      ↓
Persona
      ↓
Customer Journey
      ↓
Positioning
      ↓
Brand Message
      ↓
Tone
      ↓
Visual Direction
```

사용자는 모든 결과물을 처음부터 다시 만드는 것이 아니라 **변경된 부분을 중심으로 AI에게 수정 요청**할 수 있다.

중요한 변경은 다음 구조를 따른다.

```text
사용자 요청
   ↓
AI 제안
   ↓
영향 요소 분석
   ↓
변경사항 미리보기
   ↓
사용자 승인
   ↓
BrandState Mutation
   ↓
History 기록
```

AI가 사용자 동의 없이 브랜드 전략 전체를 임의로 덮어쓰지 않는 것이 원칙이다.

# 4. 핵심 가치 제안

NAME TAG의 핵심 가치는 다음 5가지다.

## ① Context

사용자의 사업과 브랜드에 대한 맥락을 지속적으로 유지한다.

## ② Structure

흩어진 아이디어를 사업/시장/고객/브랜드/디자인 구조로 정리한다.

## ③ Intelligence

AI가 필요한 시점에 시장조사, 경쟁사 분석, 고객 분석 등을 수행한다.

## ④ Consistency

사업과 브랜드의 각 요소가 서로 충돌하지 않도록 연결한다.

## ⑤ Workspace

완성된 결과물을 사용자가 직접 수정하고 계속 발전시킬 수 있다.

# 5. 핵심 사용자

초기 핵심 사용자는 다음과 같다.

| 사용자 | 주요 니즈 |
|---|---|

| 대학생 창업/프로젝트 사용자 | 프로젝트를 하나의 사업/브랜드로 정리 |

| 사이드 프로젝트 개발자 | 서비스의 사업/브랜드 구조화 |

초기에는 **무언가를 실제로 만들고 있는 사람**을 핵심 사용자로 설정한다.

# 6. 사용자 경험

사용자에게 O/A/B/C/DE라는 내부 단계는 보여주지 않는다.

기존:

```text
O → A → B → C → DE → PDF
```

변경:

```text
사용자
  ↕
AI Consultant
  ↕
Brand Workspace
```

사용자는 AI와 자연스럽게 대화하면서 서비스를 만들어간다.

예:

> 사용자: 대학생을 위한 AI 공부 서비스를 만들고 싶어요.

> AI: 좋아요. 먼저 이 서비스가 기존 공부 방식에서 어떤 문제를 해결하려는지 알아볼게요.

AI는 필요하면 질문하고, 필요한 경우 조사하고, 결과를 Workspace의 적절한 위치에 제안한다.

# 8-A. 사용자 데이터 소유권

모든 사용자 데이터는 요청을 보낸 사용자와 현재 Brand의 권한을 기준으로 조회/수정한다.

```text
Request
 ↓
Authenticated User
 ↓
Brand Membership / Role Check
 ↓
Resource Access
```

다음 데이터는 기본적으로 `brand_id`를 가진다.

```text
Conversation
Message
ResearchJob
ResearchReport
Document
Block
Asset
History
Decision
```

또한 변경/승인 행위에는 `actor_user_id` 또는 `created_by` / `approved_by` / `applied_by`를 기록한다.

AI가 `user_id`를 직접 입력받아 다른 사용자의 데이터를 조회하는 구조는 사용하지 않는다. 인증 정보는 Backend의 request context에서 주입한다.

# 9. AI Consultant

AI Consultant는 단순한 Chatbot이 아니라 **Workspace를 읽고 제안하며 필요한 경우 변경을 실행하는 Agent 인터페이스**다.

예:

> "타겟을 대학생에서 직장인으로 바꾸고 싶어."

단순히 문장을 반환하지 않고:

```text
Target 변경
  ↓
영향 요소 탐색
  ↓
Persona / Positioning 등 변경 제안
  ↓
사용자 승인
  ↓
BrandState 반영
```

을 수행한다.

사용자에게는 내부 Skill/Tool 이름보다 **무엇이 바뀌는지**가 보여야 한다.

# 10. AI Agent 구조

```text
User
 ↓
AI Consultant Agent
 ↓
Context Manager
 ↓
Router
 ↓
Skill
 ↓
Tool
 ↓
Artifact / Proposal
 ↓
Evaluator
 ↓
User Approval (필요한 경우)
 ↓
BrandState Mutation
 ↓
Workspace / History
```

중요한 원칙:

* Agent가 모든 작업을 직접 수행하지 않는다.
* Skill이 전문 작업 흐름을 정의한다.
* Tool이 실제 행동을 수행한다.
* BrandState가 제품의 Source of Truth다.
* 중요한 변경은 사용자 승인을 거친다.

# 11. 적용할 핵심 AI 기술

## 11.1 Chain

복잡한 작업을 여러 단계로 나누어 처리한다.

```text
시장조사
 ↓
경쟁사 분석
 ↓
고객 분석
 ↓
Positioning
 ↓
Brand Strategy
```

사용자에게 내부 단계는 기본적으로 노출하지 않는다.

## 11.2 Routing

사용자의 요청을 분석하여 필요한 Skill/Research 모드를 선택한다.

```text
"타겟을 변경해줘"
→ Customer Skill

"경쟁사를 조사해줘"
→ Research Skill

"로고를 다시 만들어줘"
→ Visual / Asset Skill
```

## 11.3 Parallelism

서로 독립적인 작업을 동시에 수행할 때 사용한다.

```text
Competitor A ─┐
Competitor B ─┤
Competitor C ─┼→ Aggregate → Analysis
Market Size ──┤
Pricing ──────┘
```

## 11.4 Evaluator

중요한 생성 결과에 대해 품질 기준을 검사한다.

```text
Generate
 ↓
Evaluate
 ↓
PASS → Proposal / Save
FAIL → 제한 횟수 내 재생성
```

Evaluator 결과는 자체 평가 점수를 사용자에게 전체 노출하는 기능이 아니라 품질 제어용으로 우선 사용한다.

## 11.5 Memory

대화 전체를 단순히 장기 기억으로 사용하는 것이 아니라 중요한 의사결정을 구조화하여 BrandState와 History에 남긴다.

## 11.6 RAG

사용자가 업로드한 자료를 기반으로 AI가 필요한 정보를 검색한다.

초기에는 핵심 Agent와 Persistence가 안정된 이후 도입한다.

## 11.7 Few-shot Prompt

브랜드 이름, 포지셔닝, 스토리, SWOT 등 형식과 품질의 일관성이 중요한 작업에 적용한다.

## 11.8 Skills

반복적으로 사용하는 전문 작업을 Skill로 분리한다.

예:

```text
business-discovery
market-research
competitor-analysis
customer-analysis
positioning
naming
brand-story
visual-direction
logo-generation
brand-guide
```

# 13. Dependency System

각 요소의 관계를 관리한다.

```text
Target
 ├─ Persona
 │   └─ Customer Journey
 │
 └─ Positioning
     ├─ Message
     ├─ Tone
     └─ Visual Direction

Business Model
 ├─ Pricing
 ├─ Target
 └─ Positioning

Market Research
 ├─ Competitors
 ├─ Positioning
 └─ Strategy
```

변경 시 영향도를 표시한다.

```text
Target 변경

Persona          HIGH
Journey          HIGH
Positioning      HIGH
Message          HIGH
Tone             MEDIUM
Color            LOW
Logo             LOW
```

단, 영향도가 높다고 해서 관련 값을 자동으로 덮어쓰지 않는다.

```text
변경 감지
 ↓
영향 분석
 ↓
변경 Proposal 생성
 ↓
사용자 승인
 ↓
Mutation
```

# 14. Research System

Research는 단순 검색 기능이 아니라 **브랜드 의사결정을 위한 근거 생산 시스템**으로 정의한다.

## Quick Research

간단한 최신 정보 확인에 사용한다.

예:

* 경쟁사 3~5개 확인
* 특정 회사의 현재 가격 확인
* 공식 홈페이지 확인
* 최근 트렌드의 간단한 확인

## Deep Research

복수 출처 비교와 장문 분석이 필요한 경우 사용한다.

예:

* 시장 규모/성장률 분석
* 복수 경쟁사 비교
* 시장 진입 가능성 분석
* 고객 검증
* 사업 모델 비교

전체 Research 구조:

```text
User Request
 ↓
Research Mode 판단
 ↓
Quick 또는 Deep
 ↓
Sources
 ↓
Report
 ↓
Finding
 ↓
Strategic Implication
 ↓
Brand Change Proposal
 ↓
User Approval
 ↓
BrandState
```

Research 결과는 자동으로 BrandState를 수정하지 않는다.

# 18-A. 사용자별 사용량과 운영 기반

로그인 기능의 또 다른 목적은 기능 사용량을 사용자 단위로 분리하는 것이다.

```text
UsageEvent
├── user_id
├── brand_id
├── feature
├── model
├── request_id
├── input_tokens
├── output_tokens
├── duration_ms
├── status
└── created_at
```

예:

```text
user_001
 ├── chat 32회
 ├── quick research 7회
 ├── deep research 1회
 └── image generation 5회
```

이 데이터는 향후 사용량 제한, 비용 분석, 요금제, 이상 사용 탐지에 활용할 수 있다. 단, 사용량 집계와 사용자 콘텐츠 자체를 동일한 데이터로 취급하지 않는다.

# 18. 성공 기준

## 사용자가

* 자신의 아이디어를 입력할 수 있다.
* AI와 대화하며 사업과 브랜드를 구체화할 수 있다.
* 조사 결과를 확인하고 근거를 볼 수 있다.
* 변경 영향을 확인할 수 있다.
* 필요한 변경을 승인할 수 있다.
* Workspace에서 결과물을 직접 수정할 수 있다.
* 과거 변경사항을 확인할 수 있다.
* PDF 또는 Brand Kit으로 결과물을 내보낼 수 있다.

## NAME TAG가

* 대화 맥락을 지속적으로 유지한다.
* BrandState를 Source of Truth로 사용한다.
* Skill과 Tool을 구분한다.
* Research 결과와 브랜드 결정을 구분한다.
* 중요한 변경을 승인 가능한 Proposal로 제공한다.
* 결과물을 지속적으로 편집 가능한 상태로 보존한다.
