# NAME TAG 개발 계획서

> 개정판: Multi-user / Authentication 반영


## 문서 목적

이 문서는 현재 NAME TAG 코드베이스에서 목표 아키텍처로 이동하기 위한 **실제 개발 순서와 완료 기준**을 정의한다.

핵심 원칙:

> 기존 기능을 한 번에 버리지 않고, FastAPI + React + Gemini를 canonical runtime으로 유지하면서 단계적으로 AI Brand Workspace로 전환한다.

---

# 3. 개발 원칙

### 원칙 1. BrandState를 Source of Truth로 한다.

동일한 브랜드 전략 정보를 여러 위치에서 중복 관리하지 않는다.

### 원칙 2. Identity와 Persistence를 먼저 확보한다.

브라우저 localStorage에 의존하는 BrandState를 장기 상태의 기준으로 사용하지 않는다. 또한 모든 장기 데이터는 인증된 사용자와 Brand 소유권/멤버십에 연결한다.

### 원칙 3. Agent는 모든 것을 직접 수행하지 않는다.

Agent는 판단하고 Skill/Tool을 호출한다.

### 원칙 4. 사용자에게 내부 Workflow를 노출하지 않는다.

O/A/B/C/DE는 내부 모듈이다.

### 원칙 5. 중요한 변경은 승인 가능해야 한다.

```text
Propose
 ↓
Review
 ↓
Approve
 ↓
Apply
```

### 원칙 6. 모든 변경은 추적 가능해야 한다.

```text
Before
After
Reason
Changed By
Timestamp
```

### 원칙 7. AI 호출을 최소화한다.

단순한 요청은 직접 처리하고 복잡한 요청에만 Agent/Research flow를 사용한다.

# 5. Phase 1 — Identity + Persistence Foundation

## 목표

NAME TAG에 **사용자 계정, 인증, Brand 소유권, 서버 persistence**를 동시에 도입한다.

로그인은 단순 UI 기능이 아니라 전체 데이터 모델의 최상위 scope가 된다.

## 기본 관계

```text
User
  ↓
BrandMember
  ↓
Brand
  ↓
BrandState / Conversation / Research / Document / Asset / History
```

## 인증

V1은 이메일/비밀번호 기반 인증과 secure session cookie를 사용한다.

```text
POST /api/auth/register
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
```

비밀번호는 Argon2id 계열 hashing을 사용하고 세션 토큰은 브라우저 localStorage에 저장하지 않는다.

## 핵심 모델

```text
users
auth_identities
sessions
user_settings
brands
brand_members
brand_states
conversations
messages
decisions
history
usage_events
audit_logs
```

Research 관련 모델은 Research Engine 단계에서 확장한다.

## 권한

```text
owner
editor
viewer
```

모든 Brand 관련 API는 인증된 사용자와 BrandMember 관계를 확인한다.

## localStorage migration

기존 사용자에게 브라우저에만 존재하는 legacy state가 있다면:

```text
localStorage
 ↓
Migration Adapter
 ↓
Authenticated User
 ↓
New Brand
 ↓
Server Persistence
```

## 사용량 추적

비용이 발생할 수 있는 AI 기능은 사용자/Brand 단위로 UsageEvent를 기록한다.

```text
user_id
brand_id
feature
model
request_id
tokens / duration / status
```

## 완료 기준

* 회원가입/로그인/로그아웃이 동작한다.
* 로그인 상태에서 현재 사용자를 조회할 수 있다.
* 한 사용자가 여러 Brand를 만들 수 있다.
* Brand마다 owner/editor/viewer 권한이 구분된다.
* 다른 사용자의 Brand ID를 알아도 데이터에 접근할 수 없다.
* 새로고침/재접속 후에도 Brand 데이터가 유지된다.
* 기존 localStorage 데이터를 안전하게 이전할 수 있다.

# 24-A. Multi-user API 권한 원칙

모든 보호 API는 다음 순서를 가진다.

```text
Request
 ↓
Session Authentication
 ↓
Current User
 ↓
Brand Membership Check
 ↓
Role Check
 ↓
Resource Query / Mutation
```

LLM의 Tool call에서 다음 값을 그대로 신뢰하지 않는다.

```text
user_id
owner_id
brand_owner_id
```

이 값들은 Backend가 세션과 DB를 기반으로 결정한다.

### 예

사용자가:

> "다른 브랜드의 로고를 보여줘"

라고 하더라도 현재 세션이 해당 Brand의 Member가 아니면 조회를 거부한다.

### Usage와 Audit

```text
UsageEvent → 비용/사용량
AuditLog   → 누가 무엇을 변경했는지
History    → BrandState 변경 이력
```

세 데이터를 목적별로 분리한다.

```text
Research를 필요한 경우에만 실행
 ↓
동일 결과 재사용
```

Agent에게 모든 Tool을 한 번에 노출하지 않는다.

# 30. 개발 완료 기준

## 사용자

* Section 이름을 몰라도 사용할 수 있다.
* AI와 대화하면서 브랜드를 만들 수 있다.
* 최신 정보가 필요하면 Research가 실행된다.
* 중요한 변경을 확인하고 승인할 수 있다.
* 결과물을 직접 수정할 수 있다.
* 과거 변경을 확인할 수 있다.
* PDF/Brand Kit을 export할 수 있다.

## NAME TAG

* 서버 persistence가 안정적이다.
* BrandState가 Source of Truth다.
* Skill과 Tool이 분리되어 있다.
* Research가 근거와 함께 저장된다.
* 자동 덮어쓰기가 방지된다.
* Legacy runtime이 제품 핵심 흐름에 개입하지 않는다.
